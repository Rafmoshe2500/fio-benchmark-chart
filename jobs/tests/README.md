# מדריך בדיקות fio

כל בדיקה כאן היא זוג קבצים:

| קובץ | תפקיד |
|---|---|
| `<test_id>.fio` | מה fio מריץ בפועל |
| `<test_id>.meta.json` | מה הבדיקה **מצהירה** שהיא מודדת — היעד, מספר הפודים, הכיוונים הצפויים |

ה־parser קורא את שניהם. אם ריצה לא עמדה במה שה־`.meta.json` הצהיר — היא **נפסלת**, ולא מדווחת עם ציון נמוך. בדיקה בלי `.meta.json` אינה ניתנת לניתוח כלל, וזה מכוון: ניחוש פרופיל משם התיקייה הוא מה שגרם בעבר לדרג עומס של 2,000 IOPS מול יעד של 15,000.

---

## שני כללים שצריך להכיר לפני שנוגעים בקובץ

### 1. `size` הוא לכל clone

```ini
size=10G
numjobs=8      ->  הדאטהסט הוא 80 GiB, לא 10
```

זה מה שהרג את `results/test4_10pods_50k_5050_32kb`: PVC של 10Gi מול דרישה של 80 GiB. כל עשרת הפודים קיבלו `ENOSPC on laying out file`, חצי ה־write מת, והדוח יצא ⚠️ WARN עם ארבעה ✅ PASS.

לחישוב:
```bash
python3 scripts/fio_capacity.py jobs/tests/<test>.fio
```

אחרי שינוי `size` או `numjobs` **חובה** להריץ `./scripts/gen_pvc_sizes.sh`, אחרת ה־preflight יסרב לפרוס.

### 2. `rate` ו־`rate_iops` הם לכל clone **ולכל כיוון**

זו הנקודה שהכי קל לטעות בה. ערך יחיד **מגביל כל כיוון בנפרד** — כלומר על job מעורב הוא נותן **פי 2** מהמספר שכתבת.

אומת מול `fio-3.41`:

```
rate_iops=100    על randrw 50/50   ->  read: IOPS=99   write: IOPS=99   (=200 סה"כ)
rate_iops=150,50 על randrw 70/30   ->  read: IOPS=149  write: IOPS=49
rate_iops=100    על randwrite      ->  write: IOPS=99                   (חד־כיווני: תקין)
```

הנוסחה לכל job מעורב:

```
per_clone  = target_iops_per_pod / numjobs
read_cap   = per_clone * rwmixread
write_cap  = per_clone * (1 - rwmixread)
rate_iops  = <read_cap>,<write_cap>
```

**היעד בשם הקובץ הוא לכל פוד.** `test1_10pods_30k_5050_4kb` = 30,000 IOPS **לפוד**, כלומר 300,000 ב־10 פודים.

## מה כל קבוצה בודקת

### test1–test4 — IOPS ברמת קלאסטר, block קטן ובינוני

עומס יציב 50/50 בקצב מוגבל, כדי לראות אם המערך עומד ביעד IOPS מוצהר תוך שמירה על latency. ההבדל בין הזוגות הוא block size (4k מול 32k) ורמת העומס (30K מול 50K לפוד).

`test2` בנוי אחרת מכולם: שמונה sections חד־כיווניים (4 read, 4 write) במקום `randrw` אחד. זה נותן חלוקה 50/50 מדויקת ומאפשר לראות read ו־write כעומסים נפרדים לגמרי. מכיוון שכל section חד־כיווני — ה־scalar `rate_iops=3750` תקין בו.

**להריץ את test1 ו־test3 יחד**: הם אותו block size בשתי רמות עומס, וההפרש ביניהם מראה איפה המערך מתחיל להיחנק.

### test5–test6 — רוחב פס, block גדול

יעד מוגדר ב־MiB/s ולא ב־IOPS. 70/30 קריאה/כתיבה, שהוא היחס האופייני לזרימת נתונים. `test6` עם 512k דורש 320 GiB לפוד — ה־PVC הכי גדול בחבילה.

### test7–test9 — בדיקות תקרה (ceiling)

**אין `rate`.** מטרתן למצוא את המקסימום, ולכן:

- **אסור להשוות את ה־latency שלהן** לבדיקות המוגבלות. עומק התור הכולל הוא `iodepth × numjobs`: ב־test7 זה **1024 בקשות במקביל**. latency במצב רוויה מודד את אורך התור, לא את המערך.
- הן רצות עם מחלקת משאבים `heavy` (8 CPU / 8Gi), כי ב־4 ליבות הלקוח נחנק לפני המערך.
- `test8` היא בדיקת read ולכן היא מקבלת `allow_file_create=0` ו־initContainer שמכין את הדאטהסט. בלי זה fio קורא קבצים sparse ומודד אוויר.

### test10–test11 — התנהגות ב־burst

שני שלבים: עומס בסיס, ואז תוספת פתאומית. שני השלבים נפרסים **מראש** ומופרדים ב־barrier של 300 שניות על שעון מוחלט — לא ב־`sleep` אחרי `helm install`. ההבדל מהותי: `helm` חוזר לפני שה־PVC נקשר וה־image נמשך, ולכן `sleep 300` מדד זמן מאז ש־helm חזר, לא מאז שהעומס התחיל.

`test11_burst_read_phase2` היא בדיקת read על PVC חדש, ולכן גם היא מקבלת prepare.

### test12–test16 — עקומת scaling

לא רצות דרך `deploy_test.sh` הרגיל אלא דרך `deploy_scale_steps.sh`. כל מדרגה (ברירת מחדל 10, 20, 40, 80 פודים) היא ריצה שלמה ונפרדת: פריסה, התחלה מסונכרנת, 420 שניות מדידה אחרי 60 שניות ramp, סיום מלא, פירוק, ואז המדרגה הבאה.

התוצאה: `results/<run_id>/step-<n>/` לכל נקודה, ו־`steps.json` שממפה מדרגה→חלון זמן.

**להשוות רק בין מדרגות של אותה ריצה** — אחרת משתנים גם תנאי המערך.

### test17 — עומס מעורב מקביל

ארבע חבילות עם block sizes שונים רצות במקביל: 13+17+7+3 = 40 פודים, כולן מתחילות באותו רגע. זה הכי קרוב לסביבת production אמיתית, שבה לא רץ workload אחיד.

### test_example — הרצה מקומית

קטנה (2 GiB לפוד, מחלקת משאבים `light`) ומיועדת לאמת שהצינור עובד לפני שמזמינים 40 פודים ו־8 טרהבייט.

## להוסיף בדיקה חדשה

1. `jobs/tests/<test_id>.fio` — העתק בלוק `[global]` מבדיקה קיימת כדי לשמור על policy אחיד (`ramp_time`, `randseed`, buffers, time-series logs). בלי זה אי אפשר להשוות אותה לשאר.
2. חשב את ה־rate לפי הנוסחה למעלה. **אל תשתמש ב־scalar על job מעורב.**
3. `jobs/tests/<test_id>.meta.json` — לפי הסכמה של קובץ קיים. השדות `replicas`, `numjobs`, `expected_directions`, `runtime_s`, `rate_limited` הם חובה.
4. `./scripts/gen_pvc_sizes.sh`
5. אמת:
   ```bash
   docker run --rm -v "$PWD/jobs:/jobs" rafmoshe2500/fio:3.41 fio --parse-only /jobs/tests/<test_id>.fio
   cd scripts && python3 -m unittest discover -s tests
   ```

הטסט `RealMetaFilesTest` נכשל אוטומטית אם הוספת `.fio` בלי `.meta.json` תואם.

## מה שינוי ב־`.fio` מחייב

| שינית | חייב לעדכן |
|---|---|
| `size` או `numjobs` | `./scripts/gen_pvc_sizes.sh` + `dataset_gib_per_pod` ב־meta |
| `rate` / `rate_iops` | `target_iops_per_pod` / `target_bw_mibps_per_pod` ב־meta |
| `runtime` | `runtime_s` ב־meta |
| `rw` | `expected_directions` ו־`rw_mix_read` ב־meta |

אם ה־meta לא תואם, ה־parser יפסול ריצות תקינות — או גרוע מזה, יאשר ריצות פגומות.
